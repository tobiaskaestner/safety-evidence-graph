# Knowledge Graph Design Summary
## Auditable Evidence for IEC 61508 — Design Session Notes

---

## 1. Purpose and Goals

The system has two distinct but complementary goals:

**Goal 1 — Point-in-time proof**
At a specific moment (identified by a test run ID and git SHAs as provenance
metadata), every requirement in scope is implemented, tested, and the evidence
is internally consistent. This is the audit submission artefact — static,
immutable once generated, answering the IEC 61508 auditor's question: *"prove
to me that your software does what you say it does."* The Merkle root is the
cryptographic fingerprint of this proof.

**Goal 2 — Continuous integrity monitoring**
As the codebase evolves, automatically detect which evidence chains have
broken, which links have gone suspect, and surface exactly what needs human
attention. This turns the graph from a one-time audit exercise into a
continuous engineering quality signal.

These two goals have different consumers: Goal 1 serves the auditor
(external, periodic, formal); Goal 2 serves the engineering team (internal,
continuous, operational).

## 2. Node Types

### 2.1 Requirement
- **Source:** repo A (sphinx-needs `.rst` files)
- **ID:** manually assigned (e.g. `REQ-042`)
- **Content:** sphinx-needs item text body and fields
- **Hash structure:** single `node_hash` (purely textual, no intent/execution split)
- **Authored by:** Requirements Engineer

### 2.2 Test Specification
- **Source:** repo B (doxygen comment above test function + test function body)
- **ID:** manually assigned (e.g. `TS-017`)
- **Content:** test intent (doxygen) + test execution logic (function body)
- **Hash structure:**
  - `spec_hash` — hash of doxygen comment (the *intent*)
  - `impl_hash` — hash of test function body (the *execution logic*)
  - `node_hash` — aggregate of `spec_hash` + `impl_hash`
- **Authored by:** Test Engineer

### 2.3 Implementation
- **Source:** repo B (doxygen comment in `.h` + function body in `.c`)
- **ID:** function name (e.g. `auth_validate`)
- **Content:** API design (doxygen) + implementation (function body)
- **Hash structure:**
  - `api_hash` — hash of doxygen comment in header (the *API design*)
  - `body_hash` — hash of function body in `.c` (the *implementation*)
  - `node_hash` — aggregate of `api_hash` + `body_hash`
- **Authored by:** Software Engineer

### 2.4 Test Outcome
- **Source:** repo C (test runner output, text files)
- **ID:** derived from test run ID + test case ID (e.g. `RUN-44/TS-017`)
- **Content:** pass/fail result and execution metadata for a specific test in a specific run
- **Hash structure:** single `node_hash` (generated artefact, no intent/execution split)
- **Generated by:** CI pipeline (test runner + extractor)
- **Grouped by:** test run ID (all outcomes from one execution share a run ID)

### 2.5 Hash Structure Symmetry

| Node Type | "Intent" sub-hash | "Execution" sub-hash | Aggregate |
|---|---|---|---|
| Requirement | — | — | `node_hash` |
| Test Specification | `spec_hash` (doxygen) | `impl_hash` (test body) | `node_hash` |
| Implementation | `api_hash` (doxygen/`.h`) | `body_hash` (`.c`) | `node_hash` |
| Test Outcome | — | — | `node_hash` |

The sub-hash split for Test Specification and Implementation allows distinguishing
"intent changed" from "execution changed" — a weaker form of suspicion than
both changing simultaneously.

## 3. Relationship Types and Propagation Rules

### 3.1 Relationship Matrix

| Source ↓ \ Target → | Requirement | Test Spec | Implementation | Test Outcome |
|---|---|---|---|---|
| **Requirement** | refines | — | — | — |
| **Test Spec** | verifies | — | — | — |
| **Implementation** | implements | — | calls | — |
| **Test Outcome** | — | confirms | witnesses | — |

All edges are directed upward in the V-model (from evidence toward claim),
except **calls** which follows call direction (caller → callee).

### 3.2 Suspicion Propagation Rules

| Relationship | Propagation | Rationale |
|---|---|---|
| refines | ⚡ Strong | Child requirement's validity depends on parent's content |
| verifies | ⚡ Strong | Test spec written against a specific requirement state |
| implements | ⚡ Strong | Implementation written against a specific requirement state |
| calls | ○ None | Structural/architectural; callee change doesn't invalidate caller's design intent |
| confirms | ✕ Sink | Test outcomes are leaves; no upward propagation |
| witnesses | ✕ Sink | Test outcomes are leaves; no upward propagation |

### 3.3 Link States

A link has four possible states, determined by two independent signals:

| Own content changed? | Dependencies changed? | State |
|---|---|---|
| No | No | **Active** — full integrity confirmed |
| Yes | No | **Directly outdated** — immediate review needed |
| No | Yes | **Transitively suspect** — dependency shifted, review may be needed |
| Yes | Yes | **Doubly outdated** — full re-review required |

### 3.4 Schema Constraint
A Test Outcome node is only valid as audit evidence if it has **both** a
`confirms` edge (to a Test Specification) and a `witnesses` edge (to an
Implementation). A node with only one of the two is incomplete and must be
flagged.

## 4. Merkle Hash Structure

### 4.1 Concept Mapping

| Merkle Concept | This Model |
|---|---|
| Prover | Proof generator tool, operated by Functional Safety Manager |
| Verifier | Auditor, using graph query tool in read-only mode |
| Claim | "Requirement REQ-042 is satisfied at test run RUN-44" |
| Proof | Merkle root of the evidence subgraph for REQ-042 at RUN-44 + hash path from each leaf to root |
| Witness | Set of node hashes and edge hash snapshots constituting the evidence chains — the `confirms`, `witnesses`, `verifies`, `implements` edges and their endpoint node hashes |

Note: **witness** has a dual meaning — it is both a Merkle concept (data
supporting a proof) and a relationship type (`witnesses` edge from test outcome
to implementation). This is intentional: the `witnesses` edge cryptographically
binds the test outcome to the specific implementation version it tested.

### 4.2 Merkle Hash Computation

Each node carries two hashes:
- `content_hash` — hash of the node's own content (= `node_hash`)
- `merkle_hash` — hash of `content_hash` combined with the `merkle_hash` values
  of all nodes this node depends on via strong-propagation edges

```
merkle_hash(N) = H(node_hash(N) || sorted(merkle_hash(dep) for dep in strong_deps(N)))
```

Only **refines**, **verifies**, and **implements** edges participate in Merkle
hash computation. **calls**, **confirms**, and **witnesses** do not.

### 4.3 Evidence Package Structure

For a given requirements scope R and test run T, the evidence package contains:

- **Header:** graph snapshot ID, test run ID, git SHAs of repos A/B/C as
  provenance metadata
- **Merkle root:** single hash fingerprinting the entire evidence state
- **Node manifest:** list of all node IDs and their `node_hash` values at
  snapshot time
- **Evidence chains:** one bundle per requirement — the connected path from
  test outcomes through the V-model to the requirement, with all link states
- **Coverage report:** requirements with incomplete chains explicitly flagged
  (missing verifies, missing witnesses, suspect links)

## 6. Tool Catalogue

### 6.1 Content Store
Git repositories (repos A, B, C, G) providing versioned, authored,
immutable-once-committed storage. Git log provides provenance metadata
(who changed what, when) for individual nodes without duplicating it in
the graph.

### 6.2 Authoring Tools
Tools through which humans create and edit node content. Graph-unaware —
they produce content that the graph system ingests.
- **Sphinx-needs** — requirements authoring (repo A)
- **Doxygen + C toolchain** — API design and implementation authoring (repo B)
- **Test framework** — test specification (doxygen) and test body authoring (repo B)

### 6.3 Extractor
Parses content from authoring tools, identifies node boundaries, computes
hashes, produces structured node records for ingestion. One extractor per
content type:
- **Sphinx-needs extractor** — parses `.rst`, extracts need items, computes `node_hash`
- **Doxygen/C extractor** — parses `.h`/`.c`, extracts function declarations,
  doxygen comments, function bodies; computes `api_hash`, `body_hash`, `node_hash`
- **Test spec extractor** — parses test files, extracts doxygen comments and
  test bodies; computes `spec_hash`, `impl_hash`, `node_hash`
- **Test outcome extractor** — parses test runner output, maps results to test
  spec IDs, computes `node_hash`

### 6.4 Graph Tooling
Operates on repo G. Four distinct functions:
- **Graph builder** — ingests extractor output, creates/updates nodes, manages
  edge definitions, computes and stores Merkle hashes
- **Graph query** — answers questions: coverage gaps, link states, suspect
  chains, node history, evidence chain traversal
- **Graph manipulator** — handles human affirmations, updates edge hash
  snapshots, records review events with authorship
- **Proof generator** — given a requirements scope and test run ID, assembles
  and validates the complete evidence package

### 6.5 CI Pipeline
Server-side enforcement and notification. Functions:
- **Extractor trigger** — on push to repo A, B, or C, runs appropriate extractor
- **Graph builder trigger** — feeds extractor output to graph builder, updates
  node hashes in repo G
- **Suspect link detector** — compares new node hashes against stored edge
  snapshots, marks affected edges suspect
- **Notifier** — routes suspect link alerts to responsible role by edge type:
  - Suspect **refines** → Requirements Engineer
  - Suspect **implements** → Software Engineer
  - Suspect **verifies** → Requirements Engineer + Test Engineer
  - Suspect **confirms** / **witnesses** → Test Engineer
- **Enforcement gate** — blocks merge/release if suspect links exist above
  configured severity threshold for in-scope requirements. **calls** links
  exempt from gate.

## 7. Human Roles

### 7.1 Role Definitions

**Requirements Engineer**
Authors and maintains requirement nodes. Reviews and affirms suspect **refines**
and **verifies** links (from requirement side). Defines requirements scope for
audit submissions. Does not own the graph.

**Software Engineer**
Authors and maintains implementation nodes (doxygen + C). Reviews and affirms
suspect **implements** and **calls** links. Does not own the graph.

**Test Engineer**
Authors and maintains test specification nodes. Executes test suite, producing
test outcome nodes. Reviews and affirms suspect **verifies** (from test spec
side), **confirms**, and **witnesses** links. Does not own the graph.

**Functional Safety Manager (FSM)**
Owns repo G and the graph schema. Defines and maintains node types and
relationship types. Maintains extractor tooling and CI hooks. Generates and
submits evidence packages for audit. Does **not** own or author content in
repos A, B, or C — this boundary is a hard constraint. Is the **prover** in
Merkle terms.

**Auditor**
External consumer of evidence packages. Read-only access to graph query tool
and proof generator output. Does not author content or graph structure. Is the
**verifier** in Merkle terms.

### 7.2 Role × Task × Tool × Goal Matrix

| Role | Task | Tool Function | Goal |
|---|---|---|---|
| Requirements Engineer | Author requirement | Sphinx-needs | Requirement node content created |
| Requirements Engineer | Review suspect link | Graph query + manipulator | Suspect link affirmed or requirement updated |
| Requirements Engineer | Define audit scope | Graph query | Requirements package scoped for proof |
| Software Engineer | Author implementation | Doxygen + C toolchain | Implementation node content created |
| Software Engineer | Review suspect link | Graph query + manipulator | Suspect **implements** or **calls** link affirmed or implementation updated |
| Test Engineer | Author test spec | Doxygen + test framework | Test spec node content created |
| Test Engineer | Execute test suite | Test framework + extractor | Test outcome nodes created in repo C |
| Test Engineer | Review suspect link | Graph query + manipulator | Suspect **confirms** or **witnesses** link affirmed or test spec updated |
| Functional Safety Manager | Define graph schema | Graph manipulator | Node/edge types formally specified |
| Functional Safety Manager | Maintain extractors + CI | CI pipeline | Automated hash extraction and suspect detection live |
| Functional Safety Manager | Generate evidence package | Proof generator | Immutable audit artefact produced |
| Functional Safety Manager | Submit to auditor | Proof generator + graph query | Evidence package delivered with Merkle root |
| Auditor | Verify evidence package | Proof generator + graph query | Evidence package accepted or gaps identified |
| CI Pipeline | Detect content change | Extractor trigger | Node hashes recomputed |
| CI Pipeline | Update graph state | Graph builder trigger | Repo G updated atomically with content change |
| CI Pipeline | Flag suspect links | Suspect link detector | Affected edges marked, responsible roles notified |
| CI Pipeline | Enforce quality gate | Enforcement gate | Release blocked if suspect links in scope |

## 8. What an Evidence Chain Looks Like

The atomic unit of proof the graph produces, for a single requirement:

> *"Requirement REQ-042 is satisfied, as evidenced by the fact that test spec
> TS-017 was written to verify it (link: active), function `auth_validate()`
> was written to implement it (link: active), test outcome TO-291 from run
> RUN-44 confirms that TS-017 passed (link: active), TO-291 witnesses the
> version of `auth_validate()` whose node_hash was `a3f9...` (link: active),
> and all of those nodes had consistent content at the time the evidence was
> collected, as attested by the Merkle root `7f2a...`."*

The full audit evidence package is the collection of such statements, one
bundle per requirement in scope, plus the coverage report for any gaps.

## 10. Separate Session: TSF Layer Exploration

A separate exploration plan has been saved examining how the integrity layer
(this system) relates to a trust scoring layer (as implemented by Eclipse TSF).
See: `tsf_layer_exploration_plan.md`

Key hypothesis: the integrity layer is a precondition checker for the trust
scoring layer. A clean integrity state is necessary but not sufficient for a
high trust score. The scoring layer adds evidence *completeness* — not just
"are links valid?" but "are there enough of the right kinds of links to support
each claim?"
