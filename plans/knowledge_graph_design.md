# Knowledge Graph Design Summary
## Auditable Evidence for IEC 61508 — Design Session Notes

---

## 1. Purpose and Goals

The system has two distinct but complementary goals:

**Goal 1 — Point-in-time proof**
At a specific moment (identified by a test run ID and git SHAs as provenance
metadata), every requirement in scope is implemented, tested, and the evidence
is internally consistent. This is the audit submission artefact — static,
immutable once generated, answering the IEC 61508 auditor's question: *"prove
to me that your software does what you say it does."* The Merkle root is the
cryptographic fingerprint of this proof.

**Goal 2 — Continuous integrity monitoring**
As the codebase evolves, automatically detect which evidence chains have
broken, which links have gone suspect, and surface exactly what needs human
attention. This turns the graph from a one-time audit exercise into a
continuous engineering quality signal.

These two goals have different consumers: Goal 1 serves the auditor
(external, periodic, formal); Goal 2 serves the engineering team (internal,
continuous, operational).

---

## 2. Node Types

Five node types exist. Four are content nodes (sourced from git repos A/B/C);
one is a graph-level assertion node (sourced from repo G).

### 2.1 Requirement
- **Source:** repo A (sphinx-needs `.rst` files)
- **ID:** manually assigned by Requirements Engineer (e.g. `REQ-042`)
- **Discovery:** automatic — the extractor finds all sphinx-needs items on
  every CI run against repo A
- **Content:** sphinx-needs item text body and fields
- **Hash structure:** single `node_hash` (purely textual, no intent/execution
  split)
- **Relationship declaration:** `links:` field in sphinx-needs item declares
  **refines** edges (child requirement declares what it refines)
- **Authored by:** Requirements Engineer

### 2.2 Test Specification
- **Source:** repo B (doxygen comment above test function + test function body)
- **ID:** manually assigned via `@testcase-id` doxygen tag (e.g. `TS-017`)
- **Discovery:** marker-based — extractor only processes functions carrying
  `@testcase` doxygen tag
- **Content:** test intent (doxygen comment) + test execution logic (function
  body)
- **Hash structure:**
  - `spec_hash` — hash of doxygen comment (the *intent*)
  - `impl_hash` — hash of test function body (the *execution logic*)
  - `node_hash` — aggregate of `spec_hash` + `impl_hash`
- **Relationship declaration:** `@verifies REQ-042` doxygen tag declares
  **verifies** edges; many-to-many supported via multiple tags
- **Authored by:** Test Engineer

### 2.3 Implementation
- **Source:** repo B (doxygen comment in `.h` + function body in `.c`)
- **ID:** function name (e.g. `auth_validate`) — locator for extractor only,
  not a semantic anchor for evidence
- **Discovery:** marker-based — extractor only processes functions carrying
  `@safety` doxygen tag in header
- **Content:** API design (doxygen comment in `.h`) + implementation (function
  body in `.c`)
- **Hash structure:**
  - `api_hash` — hash of doxygen comment in header (the *API design*)
  - `body_hash` — hash of function body in `.c` (the *implementation*)
  - `node_hash` — aggregate of `api_hash` + `body_hash`
- **Relationship declaration:** `@implements REQ-042` doxygen tag declares
  **implements** edges; many-to-many supported via multiple tags. Also used
  by extractor to notify SE when a referenced requirement changes.
- **Authored by:** Software Engineer
- **Note:** no `@node-id` tag needed. Function name is sufficient as a locator.
  A rename that leaves the doxygen comment and `@implements` tags intact is
  not a meaningful change to the evidence.

### 2.4 Test Outcome
- **Source:** repo C (test runner output, text files)
- **ID:** derived automatically: `{run_id}/{testcase_id}` (e.g. `RUN-44/TS-017`)
- **Discovery:** fully automatic — no markers needed; every test result for a
  function with a corresponding `@testcase`-tagged spec produces a node
- **Content:**
  ```
  run_id:         RUN-44
  spec_id:        TS-017
  repo_b_sha:     d4e5f6...     # git SHA of repo B at test execution time
                                # conservative binding — full repo, not
                                # function level. Any repo B change requires
                                # a new test run.
  outcome:        PASS | FAIL | ERROR | SKIPPED
  timestamp:      2024-03-15T14:32:00Z
  node_hash:      H(all of the above)
  ```
- **Hash structure:** single `node_hash` over all content fields
- **Edges created automatically:**
  - `confirms` → test spec identified by `spec_id`
  - `witnesses` → repo B at `repo_b_sha`
- **Immutability:** test outcome nodes are never updated. A new test run
  produces new nodes. Old nodes are retained permanently as historical record.
- **Generated by:** CI pipeline (test runner + test outcome extractor)
- **Grouped by:** test run ID

**On the witnesses relationship:**
The `repo_b_sha` field *is* the witnesses binding — it records which state of
the implementation repo was under test. The test spec is written against the
requirement, not against a specific function. The witnesses link says:

> *"Test Case TS-017, which verifies REQ-042, was executed against the
> implementation under test at repo B @ d4e5f6..., and the outcome was
> PASS/FAIL."*

This means:
- No explicit function-level link between test spec and implementation is needed
- Renames are completely transparent — a rename is just a different repo SHA
- The enforcement gate checks whether repo_b_sha matches current HEAD of repo B,
  flagging drift between test execution and current implementation state

### 2.5 Waiver
- **Source:** repo G
- **ID:** manually assigned by FSM (e.g. `WAV-001`)
- **Discovery:** N/A — created explicitly by FSM via graph manipulator tool
- **Content:**
  ```
  waiver_id:      WAV-001
  outcome_id:     RUN-44/TS-017
  justification:  "Known timing issue in test harness, not in production code.
                   See issue tracker #4521."
  expiry:         2024-06-15              # optional but recommended
  node_hash:      H(waiver_id || outcome_id || justification || expiry)
  ```
- **Provenance (from git log, not stored in content):**
  - `approver` — extracted from git committer identity in repo G at proof
    generation time
  - `approved_at` — extracted from git commit timestamp in repo G
  - Committer must appear in `fsm_authorised_committers.yaml` in repo G with
    a valid date range covering the commit date
- **Hash structure:** single `node_hash` over content fields only. `approver`
  and `approved_at` are provenance metadata, not content — consistent with
  how implementation node provenance is handled.
- **Relationship:** `excuses` → Test Outcome (the only edge type that points
  *to* a test outcome rather than away from it)
- **Owned by:** Functional Safety Manager exclusively — no other role can
  create or approve a waiver
- **Immutability:** waivers are append-only. A superseded waiver is retired
  by creating a new waiver, never by editing the old one. The audit trail of
  waivers is as clean as the audit trail of test outcomes.

### 2.6 Hash Structure Summary

| Node Type | "Intent" sub-hash | "Execution" sub-hash | Aggregate |
|---|---|---|---|
| Requirement | — | — | `node_hash` |
| Test Specification | `spec_hash` (doxygen) | `impl_hash` (test body) | `node_hash` |
| Implementation | `api_hash` (doxygen/`.h`) | `body_hash` (`.c`) | `node_hash` |
| Test Outcome | — | — | `node_hash` |
| Waiver | — | — | `node_hash` |

The sub-hash split for Test Specification and Implementation allows
distinguishing "intent changed" from "execution changed" — a weaker form of
suspicion than both changing simultaneously.

### 2.7 Node Type × Repo × Owner Summary

| Node type | Repo | Authored/generated by | Owned by |
|---|---|---|---|
| Requirement | A | Requirements Engineer | Requirements Engineer |
| Test Specification | B | Test Engineer | Test Engineer |
| Implementation | B | Software Engineer | Software Engineer |
| Test Outcome | C | CI pipeline | Test Engineer / CI |
| Waiver | G | Functional Safety Manager | FSM exclusively |

## 3. Authoring Marker Ecosystem

Each node type is identified within its authoring tool by a distinct marker.
Authoring tools are graph-unaware — markers are the interface between content
and graph.

| Node type | Discovery marker | ID | Relationship tag(s) |
|---|---|---|---|
| Requirement | sphinx-needs `.. need::` | Manual ID field | `links:` field (refines) |
| Implementation | `@safety` doxygen tag | Function name | `@implements REQ-xxx` |
| Test Specification | `@testcase` doxygen tag | `@testcase-id TS-xxx` | `@verifies REQ-xxx` |
| Test Outcome | N/A (auto-generated) | `{run_id}/{testcase_id}` | N/A (auto-derived) |
| Waiver | N/A (graph tool) | Manual ID by FSM | N/A (graph tool) |

## 4. Relationship Types and Propagation Rules

### 4.1 Relationship Matrix

| Source ↓ \ Target → | Requirement | Test Spec | Implementation | Test Outcome | Waiver |
|---|---|---|---|---|---|
| **Requirement** | refines | — | — | — | — |
| **Test Spec** | verifies | — | — | — | — |
| **Implementation** | implements | — | calls | — | — |
| **Test Outcome** | — | confirms | witnesses* | — | — |
| **Waiver** | — | — | — | excuses | — |

*witnesses: the `witnesses` relationship is a binding to a repo B git SHA,
not to a specific implementation node. See section 2.4.

All edges are directed upward in the V-model (from evidence toward claim),
except **calls** (follows call direction: caller → callee) and **excuses**
(waiver → test outcome, the only downward edge).

### 4.2 Suspicion Propagation Rules

| Relationship | Propagation | Resolution mechanism |
|---|---|---|
| refines | ⚡ Strong | Human affirmation by Requirements Engineer |
| verifies | ⚡ Strong | Human affirmation by RE + Test Engineer |
| implements | ⚡ Strong | Human affirmation by Software Engineer |
| calls | ○ None | N/A — structural only |
| confirms | ✕ Sink | New test run required |
| witnesses | ✕ Sink | New test run required |
| excuses | ✕ Sink | N/A — waiver is terminal |

**Key principle:** for `confirms` and `witnesses` edges, affirmation is not a
valid resolution mechanism. The only valid resolution is a new test run
producing fresh outcome nodes against the current implementation.

### 4.3 Link States

A link has four possible states, determined by two independent signals:

| Own content changed? | Dependencies changed? | State |
|---|---|---|
| No | No | **Active** — full integrity confirmed |
| Yes | No | **Directly outdated** — immediate review needed |
| No | Yes | **Transitively suspect** — dependency shifted, review may be needed |
| Yes | Yes | **Doubly outdated** — full re-review required |

### 4.4 Schema Constraints

- A Test Outcome node is only valid as audit evidence if it has **both** a
  `confirms` edge and a `witnesses` binding. Either alone is incomplete.
- A suspect link only blocks proof generation for scopes whose evidence chains
  pass through that link. A node's membership in a scope does not make all of
  its links relevant to that scope.
- Proof generation is **per-scope**: suspect links outside the defined
  requirements scope are irrelevant to that proof.

## 5. Error Handling Contract

A unified two-tier severity model applies across all extractors:

| Severity | Blocks commit? | Blocks proof generation? |
|---|---|---|
| Error | Yes | Yes |
| Warning | No | Yes |
| Info | No | No* |

*Info items appear in the coverage report but do not prevent proof generation.

### Per-condition table

**Requirements extractor:**

| Condition | Severity |
|---|---|
| Duplicate requirement ID | Error |
| Broken `links:` reference (parent ID not found) | Warning |

**Implementation extractor:**

| Condition | Severity |
|---|---|
| `@safety` present but no doxygen comment body | Error |
| Function body not found for tagged header | Error |
| Duplicate function name across translation units | Error |
| `@safety` present but no `@implements` tag | Warning |
| `@implements` references non-existent requirement ID | Warning |

**Test specification extractor:**

| Condition | Severity |
|---|---|
| `@testcase` present but no `@testcase-id` | Error |
| `@testcase` present but no doxygen comment body | Error |
| Test function body not found | Error |
| Duplicate `@testcase-id` across test files | Error |
| `@testcase` present but no `@verifies` tag | Warning |
| `@verifies` references non-existent requirement ID | Warning |

**Test outcome extractor:**

| Condition | Severity |
|---|---|
| Missing `repo_b_sha` | Error |
| Duplicate `run_id/testcase_id` | Error |
| `spec_id` references non-existent test spec | Warning |
| Outcome is SKIPPED, no waiver | Warning |
| Outcome is ERROR, no waiver | Warning |
| Outcome is FAIL, no waiver | Info (blocks proof) |
| Outcome is FAIL, valid waiver | Info (does not block proof) |
| Outcome is FAIL, expired waiver | Warning |
| `repo_b_sha` does not match current HEAD of repo B | Info (flagged in coverage report) |

**Core principle:**
> *A graph containing nodes with unresolved warnings or errors cannot produce
> a valid evidence package. The proof generator must refuse to generate a
> package if any in-scope node carries an unresolved warning or error.*

Warnings are deferred errors: they do not block day-to-day commits, but they
do block the FSM from producing audit evidence.

## 6. Waiver Rules

| Outcome state | Proof effect |
|---|---|
| PASS | Chain satisfied |
| FAIL, no waiver | Blocks proof generation |
| FAIL, valid waiver | Chain conditionally satisfied — waiver included in package |
| FAIL, expired waiver | Blocks proof generation — waiver must be renewed |
| SKIPPED, no waiver | Blocks proof generation |
| ERROR, no waiver | Blocks proof generation |

- Only the FSM can create or approve waivers
- Waivers are append-only and immutable once created
- Expiry dates are recommended to force periodic re-examination of known failures
- A waiver's `node_hash` participates in the Merkle computation like any other node

## 7. Merkle Hash Structure

### 7.1 Concept Mapping

| Merkle Concept | This Model |
|---|---|
| Prover | Proof generator tool, operated by Functional Safety Manager |
| Verifier | Auditor, using graph query tool in read-only mode |
| Claim | "Requirement REQ-042 is satisfied at test run RUN-44" |
| Proof | Merkle root of the evidence subgraph for REQ-042 at RUN-44 + hash path from each leaf to root |
| Witness | Set of node hashes and edge hash snapshots constituting the evidence chains |

Note: **witness** has a dual meaning — it is both a Merkle concept (data
supporting a proof) and a relationship type (`witnesses` binding from test
outcome to repo B SHA). This is intentional: the binding cryptographically
anchors the test outcome to the specific implementation state under test.

### 7.2 Merkle Hash Computation

Each node carries two hashes:
- `content_hash` — hash of the node's own content (= `node_hash`)
- `merkle_hash` — hash of `content_hash` combined with the `merkle_hash`
  values of all nodes this node depends on via strong-propagation edges

```
merkle_hash(N) = H(node_hash(N) || sorted(merkle_hash(dep) for dep in strong_deps(N)))
```

Only **refines**, **verifies**, and **implements** edges participate in Merkle
hash computation. **calls**, **confirms**, **witnesses**, and **excuses** do not.

### 7.3 The Two Subgraphs

The full knowledge graph contains two distinct subgraphs serving different
purposes. This distinction is fundamental to understanding what the Merkle
root proves.

**The design graph** — the subgraph over which the Merkle root is computed:
- Nodes: Requirements, Test Specifications, Implementations
- Edges: **refines**, **verifies**, **implements**
- Answers: "is what we said we'd build internally consistent?"
- The Merkle root is a cryptographic fingerprint of this consistency.
- Stable across test runs — the Merkle root does not change when tests are
  re-run, only when design content changes.

**The evidence graph** — the full graph, adding:
- Nodes: Test Outcomes, Waivers
- Edges: **confirms**, **witnesses**, **excuses**
- Answers: "did we actually build and test what we said we would?"
- Not part of the Merkle computation — captured separately in the evidence
  manifest.

The proof package combines both: the Merkle root proves design consistency;
the evidence manifest proves execution coverage.

### 7.4 Evidence Package Structure

The proof package has two formally distinct parts:

**Part 1 — Design proof (Merkle)**
```
part_1_design:
  merkle_root:    7f2a...       # fingerprints design graph consistency
  node_manifest:                # all in-scope node IDs + node_hashes
    - node_id:    REQ-002
      node_hash:  b3c1...
    - node_id:    TS-017
      node_hash:  a3f9...
    - node_id:    auth_validate
      node_hash:  c7b2...
```

Verifiable by: recomputing the Merkle root from the node manifest. An auditor
can independently verify this part without accessing repos A or B directly.

**Part 2 — Evidence manifest (test outcomes)**
```
part_2_evidence:
  test_run_id:    RUN-44
  repo_b_sha:     d4e5f6...     # implementation under test (conservative
                                #   binding — full repo, not function level)
  outcomes:
    - spec_id:    TS-017
      outcome:    PASS
      confirms:   REQ-002 (via active verifies link)
      witnesses:  repo B @ d4e5f6...
    - spec_id:    TS-019
      outcome:    FAIL
      waiver:     WAV-001 (valid, expires 2024-06-15)
```

Verifiable by: checking test runner records in repo C and waiver records in
repo G.

**Staleness check (Gate 3):**
```
evidence_valid =
  outcome == PASS (or excused FAIL with valid waiver)
  AND outcome.repo_b_sha == current HEAD of repo B
  AND link(ts → req).state == active
  AND link(impl → req).state == active
```

If `repo_b_sha` does not match current HEAD of repo B, the evidence manifest
is stale — test suite must be re-run. This is the conservative approach:
any change to repo B requires new test runs regardless of which functions
changed. Tests are assumed cheap enough to re-run for every new repo B state.

**Complete package:**
```
proof_package:
  scope:          [REQ-001, REQ-002, ...]
  snapshot_id:    2024-03-15T14:32:00Z
  part_1_design:  { merkle_root, node_manifest }
  part_2_evidence:{ test_run_id, repo_b_sha, outcomes, waivers }
  coverage_report:{ gaps, suspect_links, stale_outcomes }
```

The coverage report is as important as the chains themselves — demonstrating
awareness of what is incomplete is itself evidence of a controlled process.

## 8. Repository Structure

| Repo | Contents | Owned by |
|---|---|---|
| Repo A | Requirements (sphinx-needs `.rst` files) | Requirements Engineer |
| Repo B | Implementation (`.c`/`.h`) + Test Specifications (doxygen + test bodies) | Software Engineer + Test Engineer |
| Repo C | Test Outcomes (test runner output, text files) | CI Pipeline / Test Engineer |
| Repo G | Graph state (edge definitions, hash snapshots, link states, review events, waivers) | Functional Safety Manager |

**Key principle:** Repo G is the central audit artefact. Repos A, B, C are
the sources — Repo G is the evidence. An auditor does not need to understand
the codebase; they need to understand Repo G, which is a structured,
queryable record of every link, every hash, every state change, every human
affirmation, and every waiver.

## 9. Tool Catalogue

### 9.1 Content Store
Git repositories (repos A, B, C, G) providing versioned, authored,
immutable-once-committed storage. Git log provides provenance metadata
(who changed what, when) for individual nodes without duplicating it in
the graph.

### 9.2 Authoring Tools
Tools through which humans create and edit node content. Graph-unaware —
they produce content that the graph system ingests.
- **Sphinx-needs** — requirements authoring (repo A)
- **Doxygen + C toolchain** — API design and implementation authoring (repo B)
- **Test framework** — test specification (doxygen) and test body authoring (repo B)

### 9.3 Extractors
Parse content from authoring tools, identify node boundaries, compute hashes,
produce structured node records for ingestion. One extractor per content type:
- **Sphinx-needs extractor** — parses `.rst`, extracts need items, computes
  `node_hash`, reads `links:` field for **refines** edges
- **Implementation extractor** — parses `.h`/`.c`, finds `@safety`-tagged
  functions, extracts doxygen comments and function bodies, computes `api_hash`,
  `body_hash`, `node_hash`, reads `@implements` tags for **implements** edges
- **Test spec extractor** — parses test files, finds `@testcase`-tagged
  functions, extracts doxygen comments and test bodies, computes `spec_hash`,
  `impl_hash`, `node_hash`, reads `@verifies` tags for **verifies** edges
- **Test outcome extractor** — parses test runner output, maps results to
  `@testcase-id` values, captures `repo_b_sha`, computes `node_hash`, creates
  `confirms` and `witnesses` bindings

### 9.4 Graph Tooling
Operates on repo G. Four distinct functions:
- **Graph builder** — ingests extractor output, creates/updates nodes, manages
  edge definitions, computes and stores Merkle hashes
- **Graph query** — answers questions about the graph. Five named functions:
  - *Coverage query* — which requirements have complete evidence chains?
  - *Link state query* — which edges are suspect/outdated and why?
  - *Node history query* — what changed on a node and when?
  - *Evidence chain traversal* — show the full chain for a given requirement
  - *Proof readiness dashboard* — live Gate 2 status for a defined scope,
    showing structural completeness, link integrity, test outcome status, and
    overall readiness indicator (🟢/🟡/🔴)
- **Graph manipulator** — handles human affirmations, updates edge hash
  snapshots, records review events with authorship, creates waiver nodes
- **Proof generator** — given a requirements scope and test run ID, assembles
  and validates the complete evidence package; refuses generation if any
  in-scope node has unresolved warnings or errors

### 9.5 CI Pipeline
Server-side enforcement and notification. Functions:
- **Extractor trigger** — on push to repo A, B, or C, runs appropriate extractor
- **Graph builder trigger** — feeds extractor output to graph builder, updates
  node hashes in repo G
- **Suspect link detector** — compares new node hashes against stored edge
  snapshots, marks affected edges suspect
- **Notifier** — routes suspect link alerts to responsible role by edge type:
  - Suspect **refines** → Requirements Engineer
  - Suspect **implements** → Software Engineer
  - Suspect **verifies** → Requirements Engineer + Test Engineer
  - Suspect **confirms** / **witnesses** → Test Engineer
- **Gate 1 enforcement** — blocks commits that fail structural validity checks
- **Gate 3 enforcement** — blocks release tags if no valid current evidence
  package exists for the release scope

## 10. Human Roles

### 10.1 Role Definitions

**Requirements Engineer**
Authors and maintains requirement nodes via sphinx-needs. Reviews and affirms
suspect **refines** and **verifies** links (from requirement side). Defines
requirements scope for audit submissions. Does not own the graph.

**Software Engineer**
Authors and maintains implementation nodes (doxygen + C). Tags safety-relevant
functions with `@safety` and `@implements`. Reviews and affirms suspect
**implements** links. Does not own the graph.

**Test Engineer**
Authors and maintains test specification nodes. Tags test functions with
`@testcase`, `@testcase-id`, and `@verifies`. Executes test suite, producing
test outcome nodes. Reviews and affirms suspect **verifies** (from test spec
side) links. Does not own the graph.

**Functional Safety Manager (FSM)**
Owns repo G and the graph schema. Defines and maintains node types and
relationship types. Maintains extractor tooling and CI hooks. Creates waiver
nodes for known FAIL outcomes. Monitors proof readiness dashboard. Generates
and submits evidence packages for audit. Does **not** own or author content
in repos A, B, or C — this boundary is a hard constraint. Is the **prover**
in Merkle terms.

**Release Engineer**
Owns the release process. Checks that a valid, current evidence package exists
before tagging a release (Gate 3 owner). Read-only access to graph query tool
and evidence packages — does not author content, does not own the graph, cannot
create waivers. Escalates to FSM if the evidence package is stale or waivers
have expired; escalates to the engineering team if the implementation has
drifted from the tested state. Does not need to understand graph internals —
Gate 3 is a binary signal plus a structured escalation path.

**Auditor**
External consumer of evidence packages. Read-only access to graph query tool
and proof generator output. Does not author content or graph structure. Is the
**verifier** in Merkle terms.

| Role | Task | Tool Function | Goal |

| Requirements Engineer | Author requirement | Sphinx-needs | Requirement node content created |

## 11. What an Evidence Chain Looks Like

The atomic unit of proof the graph produces, for a single requirement:

> *"Requirement REQ-042 is satisfied because:*
> *(Part 1 — design) TS-017 verifies it (link: active), auth_validate()*
> *implements it (link: active), and the Merkle root 7f2a... fingerprints*
> *the consistency of this design graph at snapshot time.*
> *(Part 2 — evidence) Test outcome RUN-44/TS-017 confirms TS-017 with*
> *result PASS, witnessed against repo B @ d4e5f6..., which matches the*
> *current HEAD of repo B."*

The full audit evidence package is the collection of such statements, one
bundle per requirement in scope, plus waivers for any excused failures, plus
the coverage report for any gaps.

**The two-part structure means:**
- Part 1 (Merkle root) is stable across test runs — it only changes when
  design content changes
- Part 2 (evidence manifest) is regenerated on every test run against a
  new repo B state
- An auditor can verify Part 1 independently by recomputing the Merkle root
  from the node manifest
- An auditor can verify Part 2 independently by checking repo C test records
  and repo G waiver records

## 12. Enforcement Gates

Three distinct gates control transitions in the system. Each has a different
owner, trigger, and condition set.

| Gate | Owner | Trigger |
|---|---|---|
| Gate 1 — Commit gate | CI pipeline (automated) | Push to repo A, B, or C |
| Gate 2 — Proof gate | Functional Safety Manager | FSM requests evidence package |
| Gate 3 — Release gate | Release Engineer | Release tag candidate |

The gates form a cascade:
```
Gate 1 keeps the graph structurally valid
    ↓
Gate 2 keeps the evidence semantically complete
    ↓
Gate 3 keeps the release anchored to valid evidence
```

A failure at Gate 1 does not necessarily affect Gate 2 — if the failing commit
is outside the proof scope, Gate 2 is unaffected. A failure at Gate 2 always
blocks Gate 3 — a release cannot proceed without a valid proof.

### 12.1 Gate 1 — Commit Gate

Runs automatically on every push. Protects the graph from becoming
structurally malformed. No human decision-making involved.

**Conditions — all must pass:**
- No duplicate node IDs within a node type
- All mandatory markers present (`@testcase-id` where `@testcase` exists, etc.)
- All mandatory content present (no empty doxygen bodies on tagged functions)
- All function bodies found for tagged header declarations
- `repo_b_sha` present on all test outcome records

**On failure:** commit rejected. Pushing engineer fixes and repushes. Repo G
is not updated — graph state only changes on successful commits.

**Deliberately does NOT check:**
- Whether `@implements` or `@verifies` references exist in the graph (warning,
  not error — belongs at Gate 2)
- Whether links are suspect (monitoring concern, not a commit concern)
- Whether tests pass (test outcomes are facts, not commit conditions)

### 12.2 Gate 2 — Proof Gate

Evaluated when the FSM requests an evidence package for a defined scope.
Not a binary pass/fail — produces either a valid evidence package or a
structured gap report. The FSM uses the gap report as a work backlog.

**Conditions — all must pass for the defined scope:**

*Structural completeness:*
- Every in-scope requirement has at least one **verifies** edge
- Every in-scope requirement has at least one **implements** edge
- Every in-scope test spec has at least one test outcome from the specified run ID
- Every in-scope test outcome has both a `confirms` and a `witnesses` binding

*Link integrity:*
- All **refines**, **verifies**, and **implements** edges in scope are active
- All **confirms** and **witnesses** bindings reference nodes that exist

*Content validity:*
- No in-scope node carries an unresolved warning or error
- No broken `@implements` or `@verifies` references in scope

*Test outcome validity:*
- All in-scope test outcomes are PASS, or have a valid non-expired waiver
- No SKIPPED or ERROR outcomes without a waiver

*Waiver validity:*
- All in-scope waivers are non-expired
- All in-scope waivers have a named approver

**On failure:** proof generation refused. FSM receives structured gap report.
**On success:** evidence package generated and sealed with Merkle root.
Package is immutable from this point.

**Scope isolation principle:** suspect links only block proof generation for
scopes whose evidence chains pass through those links. Links outside scope
are irrelevant to the proof.

### 12.3 Gate 3 — Release Gate

Deliberately thin — does not re-evaluate evidence. Checks that valid evidence
already exists and is current relative to the release candidate.

**Conditions — all must pass:**
- A valid evidence package exists for the release scope (Gate 2 previously passed)
- The evidence package's `repo_b_sha` matches the release candidate commit
- No in-scope nodes have changed since the package was generated (verified by
  comparing current Merkle root against the package's Merkle root)
- All waivers referenced in the package are still non-expired

**On failure:** release blocked. Release Engineer notified with specific
failing condition. Escalation path:
- Stale proof or expired waivers → escalate to FSM
- Implementation drifted from tested state → escalate to engineering team

**On success:** release tagged. Evidence package SHA recorded in release tag
metadata — permanent auditable link between the release artefact and its
evidence.

### 12.4 Proof Readiness Dashboard

A named function of the graph query tool. Provides a live, scope-parameterised
view of Gate 2 conditions without triggering proof generation. Owned by the FSM.

**Inputs:**
- Requirements scope (named set of requirement IDs, or a tag/label)
- Test run ID (optional — if omitted, uses most recent run per test spec)

**Outputs — four panels:**

*Panel 1 — Structural completeness:* per-requirement coverage table showing
presence of verifies, implements, and test outcome edges.

*Panel 2 — Link integrity:* all suspect or outdated in-scope edges, with
type, state, responsible role, and date first flagged.

*Panel 3 — Test outcome status:* all non-PASS in-scope outcomes with waiver
status and expiry dates.

*Panel 4 — Overall readiness indicator:*
- 🟢 Ready — all Gate 2 conditions met, proof can be generated now
- 🟡 Pending — warnings exist but no hard blockers
- 🔴 Blocked — one or more hard blockers, proof generation will be refused

**Effect on FSM workflow:** the dashboard transforms proof generation from an
iterative discovery process (attempt → get gap report → fix → repeat) into a
single deliberate act. The FSM always knows exactly how far they are from a
valid proof before attempting generation.

## 14. Open Questions (Next Session Topics)

In agreed priority order:

1. **Repo G schema** — concrete data model for nodes, edges, hash snapshots,
   review events, waivers, authorised committer list
2. **Bootstrapping process** — initial affirmation of all links when the
   graph is first set up; what constitutes a valid first proof
3. **Git branching workflow** — how branching conventions interact with the
   graph; whether "on main = active" can replace explicit lifecycle states
   (draft, active, deprecated) on node types such as Requirement and Test
   Specification
4. **Authorised committer list** — `fsm_authorised_committers.yaml` in repo G
   as a versioned configuration artefact; handling of FSM role transitions;
   whether GPG signing is needed or named committer list is sufficient
5. **Shallow vs deep Merkle** — we agreed on deep (full transitive closure)
   but have not yet formally specified the sort order for sibling hashes or
   the exact hash algorithm (SHA-256 assumed)

## 15. Separate Session: TSF Layer Exploration

A separate exploration plan has been saved examining how the integrity layer
(this system) relates to a trust scoring layer (as implemented by Eclipse TSF).
See: `tsf_layer_exploration_plan.md`

Key hypothesis: the integrity layer is a precondition checker for the trust
scoring layer. A clean integrity state is necessary but not sufficient for a
high trust score. The scoring layer adds evidence *completeness* — not just
"are links valid?" but "are there enough of the right kinds of links to support
each claim?"
